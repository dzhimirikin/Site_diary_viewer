1. Назначение системы

1.1 Общие сведения

Site Diary — специализированная инженерная информационная система, предназначенная для ведения фотофиксации объектов строительства.

Система разработана для сопровождения полного жизненного цикла строительного объекта и обеспечивает централизованное хранение фотографий, инженерной информации и пользовательских комментариев.

В отличие от традиционных фотогалерей или систем управления контентом (CMS), Site Diary рассматривает фотографию не как самостоятельное изображение, а как инженерный объект, связанный с определённым этапом строительства.

1.2 Основные задачи

Система предназначена для решения следующих задач:

накопление фотофиксации строительного процесса;

привязка инженерных данных к фотографиям;

документирование выполнения строительных операций;

хранение истории изменений;

выпуск PDF-отчётов;

сопровождение объекта на протяжении всего периода строительства.

1.3 Основной объект системы

Центральным объектом системы является фотография строительного процесса.

Каждая фотография может содержать набор связанных инженерных данных:

комментарий;

фасад;

элемент;

исполнитель работ;

вид операции;

дату изменения.

Таким образом фотография превращается в полноценную инженерную запись, пригодную для анализа, поиска и формирования исполнительной документации.

1.4 Область ответственности

Site Diary не предназначен для выполнения функций ERP, BIM, PDM или систем управления строительством.

Система решает единственную специализированную задачу — ведение инженерной фотофиксации объекта.

Именно поэтому архитектура проекта максимально проста и не содержит избыточных серверных компонентов.

2. Общая концепция

2.1 Локальный проект

Основной архитектурной единицей Site Diary является локальный проект.

Проект представляет собой обычную папку на компьютере пользователя.

Вся структура проекта хранится в виде набора файлов и каталогов.

Такой подход обеспечивает:

независимость от серверов;

возможность автономной работы;

простое резервное копирование;

лёгкий перенос между компьютерами;

прозрачность структуры данных.

Локальный проект является главным источником истины для всех структурных данных системы.

2.2 Разделение ответственности

Архитектура Site Diary построена на строгом разделении ответственности между компонентами системы.

Каждый компонент отвечает только за собственную область.

Ни один компонент не должен выполнять функции другого компонента.

Такое разделение позволяет сохранять простую, предсказуемую и легко сопровождаемую архитектуру.

2.3 Источник истины

Одним из фундаментальных принципов системы является наличие единственного источника истины для каждого типа данных.

Это правило исключает конфликтующие копии информации и значительно упрощает сопровождение проекта.

Структура проекта хранится только в локальном проекте.

Пользовательские данные хранятся только в Firebase.

Настройки рабочего места хранятся только в localStorage.

Опубликованная копия проекта в GitHub не является источником истины и используется исключительно для распространения проекта.

2.5 Основной принцип архитектуры

Site Diary построен вокруг идеи, что проект принадлежит пользователю.

Все структурные данные находятся в локальном проекте.

Облачные сервисы используются только там, где это действительно необходимо.

Такой подход делает систему независимой, переносимой и устойчивой к отказам внешней инфраструктуры.

3. Структура проекта

3.1 Общая организация

Каждый проект Site Diary представляет собой самостоятельный каталог файлов.

Система не использует базы данных для хранения структуры проекта. Все данные находятся в обычной файловой системе, что обеспечивает прозрачность, простоту резервного копирования и независимость от специализированной инфраструктуры.

Типовая структура проекта имеет следующий вид:

Project/

├── project.json

├── diary.json

│

├── data/

│ ├── facades.json

│ ├── elements.json

│ ├── contractors.json

│ └── operations.json

│

├── images/

│ ├── IMG_0001.jpg

│ ├── IMG_0002.jpg

│ └── ...

│

└── logo.png

Все файлы имеют строго определённое назначение и используются соответствующими компонентами системы.

3.2 Файл project.json

Файл project.json содержит общую информацию о проекте.

В нём размещаются параметры, которые относятся ко всему проекту целиком, например:

название проекта;

заказчик;

объект строительства;

логотип проекта;

основные параметры отображения;

информация для формирования PDF.

Этот файл описывает проект как единое целое.

3.3 Файл diary.json

Файл diary.json является основным источником информации о фотографиях.

Именно он определяет состав галереи.

Для каждой фотографии хранится минимально необходимый набор сведений:

идентификатор фотографии;

имя файла;

дата съёмки;

дополнительные технические параметры.

При запуске Gallery файл diary.json полностью преобразуется в рабочую галерею.

Фотографии никогда не описываются вручную в HTML.

3.4 Каталог data

Каталог data содержит справочники проекта.

Каждый справочник располагается в отдельном JSON-файле.

data/

├── facades.json

├── elements.json

├── contractors.json

└── operations.json

Такое разделение обеспечивает:

независимое сопровождение;

простой импорт и экспорт;

минимизацию конфликтов при изменениях;

возможность повторного использования между различными проектами.

Каждый проект имеет собственный комплект справочников.

3.5 Каталог images

Каталог images содержит все фотографии проекта.

Gallery получает список фотографий из diary.json, после чего загружает соответствующие изображения из данного каталога.

Фотографии являются неизменяемыми исходными материалами проекта.

Все дополнительные сведения о фотографиях располагаются отдельно и не внедряются в изображения.

3.6 Логотип проекта

Файл logo.png содержит логотип проекта.

Он используется:

в интерфейсе Gallery;

в PDF-документах;

в титульных блоках отчётов.

Замена логотипа не требует изменения программного кода.

3.7 Независимость проекта

Каждый каталог проекта полностью автономен.

Проект можно:

скопировать;

архивировать;

перенести на другой компьютер;

опубликовать;

восстановить из резервной копии.

Никаких дополнительных действий со стороны системы не требуется.

Именно поэтому локальный проект является главным объектом управления Uploader.

4. Источники данных

4.1 Архитектурный принцип

Одним из фундаментальных правил Site Diary является использование единственного источника истины для каждого типа данных.

Каждый набор данных имеет только одно место хранения.

Это исключает рассинхронизацию информации и значительно упрощает сопровождение проекта.

4.2 Структурные данные проекта

Источник истины — локальный проект.

В нём располагаются:

project.json;

diary.json;

каталог data;

каталог images;

логотип проекта.

Изменение этих данных допускается исключительно средствами Uploader.

Gallery никогда не изменяет структуру проекта.

4.3 Пользовательские данные

Источник истины — Firebase.

В Firebase размещаются:

комментарии пользователей;

результаты классификации фотографий;

история изменений;

объекты Photo Annotation.

Эти данные создаются непосредственно в процессе эксплуатации системы и не входят в состав опубликованного проекта.

4.4 Настройки рабочего места

Источник хранения — localStorage браузера.

Здесь располагаются персональные параметры пользователя:

настройки PDF;

параметры штампа;

размеры текста;

режимы отображения;

индивидуальные предпочтения интерфейса.

Эти настройки принадлежат конкретному рабочему месту и не синхронизируются между пользователями.

4.5 Опубликованный проект

После публикации проект размещается в GitHub Pages.

Опубликованная копия используется исключительно для просмотра и распространения проекта.

Она не является источником истины.

Любые изменения структуры проекта выполняются только в локальном проекте с последующей публикацией новой версии.

4.6 Сводная схема источников данных

6. Справочники

6.1 Назначение

Справочники являются основой системы классификации фотографий.

Они содержат перечни инженерных сущностей, которые пользователь назначает каждой фотографии во время работы с проектом.

Справочники не описывают объект строительства. Они описывают возможные значения инженерной классификации.

6.2 Архитектурная концепция

Каждый проект Site Diary имеет собственный комплект справочников.

Справочники являются частью проекта и публикуются вместе с ним.

Структура хранения:

data/

├── facades.json

├── elements.json

├── contractors.json

└── operations.json

Каждый файл представляет собой независимый JSON-массив.

Между файлами отсутствуют какие-либо жёсткие связи.

6.3 Принцип независимости

Все справочники являются полностью независимыми классификаторами.

Например:

фасад не содержит список элементов;

элемент не содержит ссылку на фасад;

исполнитель не связан с конкретной операцией;

операция не знает, каким подрядчиком она выполняется.

Система сознательно не реализует объектную модель здания.

Она реализует исключительно механизм классификации фотографий.

Именно это позволяет использовать Site Diary для объектов практически любой структуры без изменения архитектуры.

6.4 Facades

Назначение

Справочник фасадов содержит перечень фасадных зон объекта.

Типичные записи:

KLF1

KLF2

A1

U1

Каждая запись имеет простую структуру.

{

"id": 1,

"name": "KLF1"

}

Поле id является внутренним идентификатором системы.

Поле name отображается пользователю.

6.5 Elements

Назначение

Справочник элементов содержит марки элементов фасада.

Типичные записи:

KLF1.1.M1

KLF1.1.M2

KLF2.3.S1

Структура записи:

{

"id": 12,

"name": "KLF1.1.M2"

}

Несмотря на внешнее сходство обозначения с фасадом, система не анализирует структуру имени.

Для Gallery это обычная текстовая строка.

6.6 Contractors

Назначение

Справочник исполнителей работ.

Типичные записи:

Иванов

Петров

ABC Facades

Структура записи:

{

"id": 3,

"name": "ABC Facades"

}

Исполнитель выбирается пользователем при описании фотографии.

Никаких дополнительных связей система не хранит.

6.7 Operations

Назначение

Справочник видов выполняемых работ.

Типичные значения:

Сборка рамы

Сборка створки

Установка фурнитуры

Установка стеклопакета

Структура записи:

{

"id": 4,

"name": "Установка стеклопакета"

}

Количество операций не ограничено.

Пользователь может полностью заменить содержимое справочника для конкретного проекта.

6.8 Правила хранения

Каждый справочник располагается в отдельном JSON-файле.

Такое решение было принято по нескольким причинам.

Простота сопровождения

Изменение одного справочника не затрагивает остальные.

Простота импорта

Можно импортировать только необходимые данные.

Например:

contractors.json

без изменения остальных файлов проекта.

Простота экспорта

Любой справочник экспортируется обычным копированием файла.

Минимизация конфликтов

Если несколько человек сопровождают проект, вероятность конфликтов при изменении отдельных файлов значительно ниже, чем при использовании одного большого JSON-документа.

Повторное использование

Справочники могут переноситься между проектами.

Например:

operations.json

можно использовать сразу в нескольких объектах.

Для этого достаточно заменить один файл.

6.9 Архитектурное правило ID

Это одно из важнейших правил всей системы.

Пользователь работает с названиями.

Система хранит только идентификаторы.

Например.

Пользователь выбирает:

KLF1

В объекте Photo Annotation сохраняется:

{

"facadeId": 1

}

Аналогично работают все остальные справочники.

{

"elementId": 12,

"contractorId": 3,

"operationId": 4

}

Таким образом:

названия можно свободно изменять;

внутренние связи не нарушаются;

объём пользовательских данных уменьшается;

ускоряется поиск;

исключается дублирование строк.

6.10 Добавление новых справочников

Архитектура допускает расширение системы.

Если в будущем потребуется добавить новый классификатор, например:

Materials

Zones

Buildings

Floors

Defects

достаточно:

создать новый JSON-файл;

добавить соответствующий selector в Gallery;

сохранить только его ID в Photo Annotation.

При этом существующая архитектура проекта останется неизменной.

Основной архитектурный принцип главы

Справочники являются независимыми классификаторами.

Они не описывают структуру здания.

Они предоставляют набор допустимых значений, которые пользователь может назначить фотографии.

Благодаря этому Site Diary остаётся простой, универсальной и масштабируемой системой без необходимости создавать сложную объектную модель строительного объекта.

7. Photo Annotation

7.1 Назначение

Центральным объектом пользовательских данных в Site Diary является Photo Annotation.

Photo Annotation представляет собой описание одной фотографии и содержит всю информацию, которую пользователь добавляет в процессе работы.

Фотография остаётся неизменяемым объектом, а вся инженерная информация хранится отдельно.

Такой подход позволяет:

не изменять оригинальные изображения;

хранить только пользовательские данные;

независимо сопровождать фотографии и комментарии;

безопасно расширять структуру данных в будущем.

7.2 Архитектурная роль

Photo Annotation является связующим звеном между фотографией и инженерными справочниками.

Схематично структура выглядит следующим образом:

Photo

│

▼

Photo Annotation

│

┌────────────┼────────────┐

▼ ▼ ▼

Facades Elements Contractors

│

▼

Operations

Таким образом фотография не содержит инженерной информации.

Она лишь имеет соответствующий объект Photo Annotation.

7.3 Структура объекта

Типичный объект имеет следующий вид.

{

"photoId": "IMG_001",

"comment": "Монтаж завершён.",

"facadeId": 1,

"elementId": 12,

"contractorId": 3,

"operationId": 4,

"updatedAt": "2026-06-24T12:00:00Z"

}

Каждое поле имеет строго определённое назначение.

7.4 Независимость фотографии

Фотография никогда не содержит:

комментариев;

инженерных данных;

сведений об исполнителях;

истории изменений.

Все эти сведения находятся исключительно в Photo Annotation.

Благодаря этому фотографии остаются неизменяемыми исходными данными проекта.

7.5 Независимость классификаторов

Каждое поле Photo Annotation является полностью независимым.

Например, пользователь может выбрать:

Facade → KLF2

Element → KLF1.1.M2

Contractor → ABC Facades

Operation → Установка стеклопакета

Даже если такая комбинация кажется необычной, система её принимает.

Gallery не анализирует инженерную корректность выбранной комбинации.

Она только сохраняет выбранные значения.

7.6 Проверка данных

Единственная проверка, выполняемая системой:

Каждый указанный идентификатор должен существовать в соответствующем справочнике.

Например.

Если

{

"operationId": 7

}

то запись с ID = 7 должна присутствовать в operations.json.

Других ограничений архитектура не накладывает.

7.7 Расширяемость

Структура Photo Annotation допускает безопасное расширение.

Например, позднее могут быть добавлены поля:

{

"materialId": 15,

"zoneId": 2,

"floorId": 5

}

Gallery автоматически сможет использовать новые классификаторы после добавления соответствующих справочников.

При этом существующие проекты останутся полностью совместимыми.

7.8 Хранение

Объекты Photo Annotation располагаются исключительно в Firebase.

Они не входят:

в project.json;

в diary.json;

в каталог data;

в опубликованный проект.

Таким образом пользовательские данные полностью отделены от структуры проекта.

8. Gallery

8.1 Назначение

Gallery является основным рабочим приложением Site Diary.

Именно через Gallery пользователь ежедневно взаимодействует с проектом.

Gallery объединяет фотографии, структуру проекта, пользовательские комментарии и настройки интерфейса в единое рабочее пространство.

8.2 Главная функция

Основой Gallery является функция:

loadDiary()

Именно она преобразует содержимое файла diary.json в рабочий интерфейс.

Рабочая галерея

Gallery никогда не содержит статически описанных фотографий.

Все элементы интерфейса создаются автоматически.

8.3 Генерация интерфейса

Во время загрузки Gallery:

считывает project.json;

считывает diary.json;

загружает изображения;

создаёт HTML-структуру;

запрашивает пользовательские данные из Firebase;

отображает готовую галерею.

Таким образом HTML является результатом работы программы, а не источником данных.

8.4 Работа с фотографиями

Для каждой фотографии Gallery отображает:

изображение;

дату;

комментарий;

назначенные классификаторы;

дополнительные служебные элементы.

Пользователь всегда работает с одной и той же моделью данных независимо от размера проекта.

8.5 Работа со справочниками

Gallery никогда не изменяет справочники.

Она:

загружает их;

отображает пользователю;

позволяет выбрать значения;

сохраняет только ID выбранных записей.

Редактирование справочников относится исключительно к Uploader.

8.6 Работа с Firebase

Gallery обращается к Firebase только для чтения и записи пользовательских данных.

Она не изменяет структуру проекта и не влияет на опубликованную версию.

Таким образом обязанности компонентов остаются строго разделёнными.

8.7 Архитектурный принцип Gallery

Gallery представляет собой рабочий клиент локального проекта.

Она не является административным приложением.

Она не управляет публикацией.

Она не изменяет структуру проекта.

Gallery отвечает только за работу пользователя с уже подготовленным проектом.

9. Формирование PDF

9.1 Назначение

Формирование PDF является одной из ключевых функций Site Diary.

Итоговый PDF-документ представляет собой инженерный отчёт, сформированный автоматически на основании данных проекта и пользовательской классификации фотографий.

PDF не является самостоятельным источником данных.

Он представляет собой результат обработки информации, уже существующей в системе.

9.2 Источники данных

При формировании PDF используются четыре независимых источника.

Каждый источник отвечает только за собственную часть информации.

9.3 Конвейер формирования

Архитектурно PDF является конечным продуктом обработки данных.

После генерации он больше не связан с исходным проектом.

9.4 Содержимое страницы

Типичная страница PDF содержит:

фотографию;

дату съёмки;

комментарий;

сведения о фасаде;

сведения об элементе;

исполнителя работ;

вид операции;

служебный штамп.

Все элементы размещаются автоматически в соответствии с текущими настройками пользователя.

9.5 Настройки оформления

Параметры оформления не входят в состав проекта.

Они сохраняются в localStorage и относятся только к конкретному рабочему месту.

Настраиваются:

формат листа;

ориентация страницы;

размеры фотографий;

размеры шрифта;

параметры штампа;

поля страницы;

интервалы между фотографиями.

Благодаря этому каждый пользователь может сформировать отчёт в удобном для себя виде, не изменяя проект.

9.6 Шрифт

Для обеспечения одинакового отображения на всех компьютерах используется единый встроенный шрифт.

isocpeur-normal.js

Использование встроенного шрифта обеспечивает:

одинаковое отображение текста;

независимость от установленных системных шрифтов;

корректное формирование PDF на любых компьютерах.

Поддерживается только прямое начертание.

Использование искусственного наклона или альтернативных начертаний не предусмотрено.

9.7 Штамп

Центром оформления каждой страницы является функция:

drawTitleBlock()

Именно она отвечает за построение служебного штампа.

В её обязанности входят:

размещение реквизитов проекта;

вывод номера страницы;

отображение логотипа;

вывод дополнительной информации.

Любые изменения оформления штампа должны выполняться исключительно в данном модуле.

Это обеспечивает единообразие оформления всех отчётов.

9.8 Архитектурный принцип

Gallery подготавливает данные.

Модуль PDF отвечает только за визуальное представление.

Разделение этих обязанностей позволяет независимо изменять:

структуру пользовательских данных;

алгоритмы формирования отчётов;

оформление страниц.

10. Интерфейс Gallery

10.1 Общая концепция

Gallery поддерживает два режима работы.

Режим определяет состав элементов интерфейса и доступные пользователю действия.

Переключение режима не изменяет данные проекта.

Меняется только способ взаимодействия пользователя с системой.

10.2 Режим VIEW

Режим VIEW предназначен для просмотра материалов.

Отображаются:

фотографии;

даты;

навигация;

основные сведения.

Скрываются:

элементы классификации;

редакторы комментариев;

служебные панели;

элементы управления PDF.

Режим VIEW используется при демонстрации проекта и просмотре материалов.

10.3 Режим LAYOUT

LAYOUT является основным рабочим режимом.

В этом режиме пользователь может:

назначать фасады;

назначать элементы;

выбирать исполнителей;

выбирать виды операций;

редактировать комментарии;

формировать PDF;

изменять параметры оформления отчётов.

Все изменения пользовательских данных сохраняются в Firebase.

10.4 Отказ от режима ADMIN

Ранее архитектура предусматривала отдельный режим ADMIN.

В ходе развития проекта было принято решение отказаться от него.

Причины:

разделение ответственности;

упрощение Gallery;

перенос административных функций в специализированное приложение.

Все функции администрирования были перенесены в Uploader.

В результате Gallery стала исключительно рабочим клиентом проекта.

10.5 Принцип отображения

Интерфейс строится динамически.

Каждый элемент создаётся программно в процессе выполнения loadDiary().

Статическое описание фотографий в HTML не допускается.

Такой подход обеспечивает:

единый алгоритм построения интерфейса;

отсутствие дублирования данных;

простоту сопровождения;

возможность автоматического масштабирования проекта.

10.6 Основной архитектурный принцип главы

Интерфейс Gallery не содержит информации о проекте.

Он является визуальным представлением данных, загруженных из локального проекта, Firebase и localStorage.

Таким образом интерфейс полностью отделён от модели данных, что соответствует общей архитектуре Site Diary.

11. Архитектурные ограничения

11.1 Назначение

Архитектурные ограничения определяют фундаментальные правила развития Site Diary.

Они являются обязательными для всех последующих изменений проекта.

Любое архитектурное решение должно соответствовать данным ограничениям.

11.2 Запрещённые архитектурные решения

В рамках проекта не допускается внедрение компонентов, противоречащих принятой архитектуре.

Backend

Не допускается создание собственного серверного приложения.

Запрещается использование:

Node.js;

ASP.NET;

PHP;

Java;

Python-сервера;

любых других серверных решений.

Gallery должна оставаться полностью клиентским приложением.

Базы данных

Не допускается использование:

SQL Server;

PostgreSQL;

MySQL;

MariaDB;

SQLite;

Oracle.

Структура проекта должна храниться исключительно в файловой системе.

Современные SPA-фреймворки

В проекте не используются:

React;

Vue;

Angular;

Svelte;

Next.js;

Nuxt.

Gallery построена на классическом HTML, CSS и JavaScript.

Такое решение обеспечивает:

минимальный размер проекта;

отсутствие процесса сборки;

простоту сопровождения;

лёгкость публикации.

TypeScript

Использование TypeScript не предусмотрено.

Проект полностью реализован на стандартном JavaScript.

Это позволяет избежать дополнительных этапов компиляции и сохранить максимально простую структуру разработки.

Docker

Использование Docker-контейнеров не требуется.

Проект должен запускаться непосредственно в браузере без промежуточной инфраструктуры.

11.3 Ограничения хранения данных

Архитектура строго разделяет ответственность между хранилищами данных.

Не допускается:

хранение структуры проекта в Firebase;

хранение справочников в Firebase;

хранение комментариев в diary.json;

хранение пользовательских настроек в проекте;

хранение фотографий в Firebase.

Каждый тип данных имеет единственный источник истины.

11.4 Ограничения интерфейса

Интерфейс Gallery должен формироваться исключительно программно.

Не допускается:

статическое описание фотографий в HTML;

ручное добавление карточек фотографий;

дублирование информации между HTML и diary.json.

Единственным источником информации о фотографиях является файл diary.json.

11.5 Ограничения развития

При дальнейшем развитии проекта необходимо соблюдать следующие правила.

Новые возможности должны:

использовать существующую архитектуру;

не нарушать разделение ответственности компонентов;

не создавать дополнительные источники истины;

не усложнять структуру проекта без объективной необходимости.

Простота архитектуры является одним из главных требований проекта.

12. Основные архитектурные принципы

12.1 Единственный источник истины

Каждый тип данных имеет только одно место хранения.

Это правило является обязательным для всех компонентов системы.

12.2 Разделение ответственности

Каждый компонент выполняет только собственные функции.

Ни один компонент не должен брать на себя функции другого.

12.3 Простота проекта

Site Diary сознательно избегает сложной архитектуры.

Проект не требует:

серверной инфраструктуры;

процесса сборки;

контейнеризации;

дополнительных служб;

сложной конфигурации.

Любой пользователь должен иметь возможность открыть опубликованный проект обычным браузером.

12.4 Независимость компонентов

Каждый компонент может развиваться независимо.

Например:

изменение Gallery не требует изменения Uploader;

изменение Firebase не влияет на структуру проекта;

изменение оформления PDF не влияет на Gallery;

изменение справочников не требует изменения архитектуры.

Такая независимость значительно упрощает сопровождение системы.

12.5 Масштабируемость

Архитектура допускает расширение без изменения базовых принципов.

Можно добавлять:

новые справочники;

новые режимы отображения;

новые параметры Photo Annotation;

новые шаблоны PDF;

новые инструменты анализа.

При этом фундаментальная архитектура остаётся неизменной.

13. Заключение

Site Diary построен вокруг идеи простого локального проекта, который полностью принадлежит пользователю.

Все структурные данные находятся в файловой системе.

Пользовательские данные хранятся отдельно.

Каждый компонент отвечает только за собственную область ответственности.

Такой подход обеспечивает:

простоту сопровождения;

высокую надёжность;

прозрачность хранения данных;

независимость от сложной инфраструктуры;

лёгкость публикации;

масштабируемость без изменения архитектурных принципов.

Ключевые принципы проекта

В качестве итогового резюме архитектуры следует руководствоваться следующими правилами.

Проект живёт на компьютере пользователя.

Локальный проект является источником истины для структуры объекта.

Firebase является источником истины для пользовательских данных.

Uploader управляет проектом.

Gallery работает с проектом.

GitHub публикует проект.

Справочники принадлежат проекту и являются независимыми классификаторами.

Пользователь работает с понятными названиями.

Система хранит только идентификаторы (ID).

Простота архитектуры важнее сложности реализации.
