Site Diary — Архитектура и техническая концепция

Назначение системы

Site Diary — специализированная инженерная система ведения фотофиксации объекта строительства.

Основные задачи:

·  накопление фотофиксации;

·  привязка инженерных данных к фотографиям;

·  хранение истории выполнения работ;

·  выпуск PDF-отчётов;

·  сопровождение объекта на протяжении жизненного цикла строительства.

Система не является обычным сайтом, CMS или фотогалереей.

Основным объектом системы является фотография строительного процесса и связанные с ней инженерные данные.

Общая концепция

Site Diary построен вокруг концепции локального проекта.

Проект существует как набор файлов на компьютере пользователя.

Все остальные компоненты системы являются инструментами публикации, просмотра и сопровождения этого проекта.

Справочники

Все справочники принадлежат проекту.

Каждый проект имеет собственный набор справочников.

Размещение:

data/

 

    facades.json

    elements.json

    contractors.json

    operations.json

Принцип справочников

Справочники являются независимыми классификаторами.

Система не реализует объектную модель фасада.

Система реализует классификацию фотографий.

Facades

Марки фасадов.

Примеры:

KLF1

KLF2

U1

A1

Пример записи:

{

  "id": 1,

  "name": "KLF1"

}

Elements

Марки элементов.

Примеры:

KLF1.1.M1

KLF1.1.M2

KLF2.3.S1

Пример записи:

{

  "id": 12,

  "name": "KLF1.1.M2"

}

Система не хранит и не контролирует связь между Element и Facade.

Contractors

Исполнители работ.

Примеры:

Иванов

Петров

ABC Facades

Пример записи:

{

  "id": 3,

  "name": "ABC Facades"

}

Operations

Типы операций.

Примеры:

Сборка рамы

Сборка створки

Пример записи:

  "id": 4,

  "name": "Установка стеклопакета"

}

Правила справочников

Каждый справочник хранится в отдельном JSON-файле.

Причины:

Простое сопровождение

Простой импорт

Простой экспорт

Простое копирование между проектами

Минимизация конфликтов

Перенос справочников

Перенос между проектами выполняется на уровне файлов.

Например:

contractors.json

может быть скопирован из одного проекта в другой.

Аналогично:

operations.json

facades.json

elements.json

Специальные форматы обмена не требуются.

Архитектурное правило ID

Человек работает с названиями.

Система хранит только ID.

Пользователь видит:

KLF1

Система хранит:

{

  "facadeId": 1

}

Это правило распространяется на все существующие и будущие справочники.

Photo Annotation

Для каждой фотографии существует объект пользовательских данных:

Photo Annotation

Он хранится в Firebase.

Пример:

{

  "photoId": "IMG_001",

 

  "comment": "...",

 

  "facadeId": 1,

  "elementId": 12,

  "contractorId": 3,

  "operationId": 4,

 

  "updatedAt": "2026-06-24T12:00:00Z"

}

Принцип Photo Annotation

Фотография рассматривается как объект, которому назначается набор независимых классификаторов.

Схема:

Photo

 

    facadeId

    elementId

    contractorId

    operationId

Система не выполняет проверку взаимной согласованности этих значений.

Допускается любая комбинация существующих записей справочников.

Единственное требование:

Любой указанный ID

должен существовать

в соответствующем справочнике.
